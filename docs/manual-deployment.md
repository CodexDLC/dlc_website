# Ручная публикация и запуск DLC

Приложение публикуется в `CodexDLC/dlc_website`. Секреты остаются в закрытом файле на сервере: `/srv/dlc/shared/.env.prod`, права `600`. Локальную рабочую копию `.env.prod` тоже нельзя добавлять в Git. Проверяйте это через `git check-ignore .env.prod`.

## Что нужно подготовить

Создать закрытый файл на компьютере из существующей локальной конфигурации:

```powershell
.venv/Scripts/python.exe scripts/prepare_prod_env.py --source-env .env --output .env.prod
```

Генератор сохраняет существующий `FIELD_ENCRYPTION_KEY`, создаёт новые пароли сервера и отказывается перезаписывать готовый файл. Значения секретов не выводит. Параметр `--fresh-database` разрешает новый ключ только при запуске с совершенно новой базой. Затем перенести файл защищённым SSH-соединением в `/srv/dlc/shared/.env.prod` и установить права `600`. Не вставлять его содержимое в чат или публичные настройки GitHub.

- `SECRET_KEY`: отдельная случайная строка Django для серверной версии.
- `DLC_DB_PASSWORD`: отдельный случайный пароль PostgreSQL. Используйте буквы и цифры, чтобы пароль безопасно входил в адрес подключения.
- `FIELD_ENCRYPTION_KEY`: если переносим существующую базу, **сохранить текущий ключ**. Новый ключ не сможет расшифровать старые данные. Для совершенно новой базы нужен новый Fernet-ключ.
- Домены и адреса: `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, `TEST_SITE_BASE_URL`, `TEST_CANONICAL_DOMAIN`. Для прототипа использовать `dlc.pinlite.dev` и `https://dlc.pinlite.dev` соответственно.
- Явно выбрать `PRIVATE_STORAGE_BACKEND` и подготовить хранение файлов. При `s3` нужны отдельные доступы к бакету; при `local` файлы сохраняются в постоянном серверном Docker volume.

Перед переносом рабочей базы остановить её изменение, сделать резервную копию и согласовать восстановление базы и файлов. Готового скрипта резервного копирования этот помощник пока не содержит. Запуск контейнеров с пустым volume сам по себе данные с компьютера не переносит. Перед обновлением уже работающего сервера также нужна резервная копия базы: откат кода не отменяет миграции.

SSH использует локальный ключ и существующий псевдоним из вашей SSH-конфигурации. Создавать новый ключ для ручного запуска не требуется. Помощник требует заранее проверенный ключ сервера в `known_hosts` и доступ без интерактивного запроса пароля. Секретный SSH-ключ не помещать ни в исходники, ни в `.env.prod`. Публичный репозиторий сервер скачивает без GitHub-токена.

## Команды на компьютере

Сначала сохранить изменения коммитом в `main` и пройти проверки проекта. Скрипт откажется работать при незакоммиченных изменениях; публикация и установка другой ветки запрещены.

```powershell
# Показать выбранный коммит; ничего не публикует и не меняет сервер.
./scripts/deploy_manual.ps1

# Только обычный push текущей ветки, без принудительной перезаписи истории.
./scripts/deploy_manual.ps1 -Push

# Опубликовать и установить именно этот коммит на подготовленный сервер.
./scripts/deploy_manual.ps1 -Push -Deploy -SshAlias '<your SSH alias>'
```

При установке SSH-псевдоним обязательно передать через `-SshAlias`; замените пример своим именем из SSH-конфигурации. Отдельный `-Deploy` устанавливает текущий коммит, который уже должен существовать в удалённом репозитории. Скрипт не создаёт коммитов, не меняет DNS и не копирует секреты.

## Что происходит на сервере

Каждый коммит получает каталог `/srv/dlc/releases/<полный SHA>`. Образ помечается тем же SHA. Используется постоянное имя Compose-проекта `dlc`, поэтому база и файлы не меняют владельца при переходе между каталогами релизов.

Порядок: проверить наличие закрытого env-файла; проверить Compose без вывода значений; собрать приложение; запустить PostgreSQL и Redis; отдельно выполнить миграции и сбор статики; запустить Django и дождаться проверки работоспособности. Удаления volumes нет. После успешной проверки работоспособности ссылка `current` указывает на установленный релиз.

Django слушает внутренний адрес сервера. Для доступа по домену отдельно нужны DNS-запись, HTTPS и обратный прокси. После запуска проверить HTTPS, вход в кабинет и переключение RU/DE. Прототип должен оставаться закрытым от индексации; overlay `compose.test-server.yml` включает этот режим.

## GitHub Secrets

Для ручного SSH-запуска GitHub Secrets не нужны: `.env.prod` находится на сервере. Существующий workflow `deploy-production.yml` пока намеренно останавливается до подключения к серверу; обычный push сайт автоматически не обновляет.

Если позже подключаем GitHub Actions, создать отдельный ограниченный ключ для автоматизации, поместить только его публичную часть на сервер, а приватную — в защищённое GitHub Environment. Список переменных и разрешений для этого процесса согласовать при его реализации. Копировать все серверные переменные в публичные Repository Variables нельзя.

прошли проверки работоспособности; обе языковые обложки отвечают внутри сервера.

пользователю деплоя. Помощник копирует туда собранные файлы после запуска Django.

скачивание документов проходит через авторизованные представления приложения.

## Основной контур рабочих данных

Рабочая база и связанные файлы перенесены с локальных Docker-контейнеров на сервер.
Выполнена проверка таблиц, файлов и клиентского доступа. Локальный исходник оставлен
для чтения, его web/nginx остановлены; дальнейшее заполнение выполняется на сервере.
Повторный импорт старого локального снимка поверх новых серверных записей запрещён.

До появления API отчёты можно заполнять через SSH: выполнять Django management
commands или существующие application services внутри контейнера web. Соблюдать
`dlc-daily-report-entry`, проверку полномочий, транзакции и сетку времени.
Перед изменениями сохранять резервную копию; не обходить проверки прямым SQL.
