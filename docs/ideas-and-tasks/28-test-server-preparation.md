# Тестовый сервер: подготовка без внешнего запуска

Состояние на 10.10.2026: `deploy/compose.test-server.yml` задаёт конфигурацию будущего тестового контура поверх production Compose. Он включает `TEST_SITE_NOINDEX=True`, строго требует выбранный HTTPS URL и явный выбор закрытого хранилища. Никакой сервер, домен, Git remote, registry или хранилище секретов этим файлом не создаётся. Доступен только локальный подготовительный шаг; внешний запуск требует утверждённых владельцем реквизитов и отдельной проверки.

## Что надо определить перед запуском

1. Выбрать отдельное доменное имя тестового контура и способ HTTPS терминации. Web в `compose.prod.yml` слушает только `127.0.0.1`; внешний proxy должен передавать `Host` и `X-Forwarded-Proto: https`, обслуживать `/static/` и не открывать `/data/private/` и `/private/`. До открытия внешнего адреса установить на этом proxy общий барьер доступа (HTTP Basic Auth, VPN или эквивалент), включая статику, медиа и страницы ошибок proxy. Проверить, что жёсткая политика HSTS в production settings допустима для выбранного домена и его поддоменов.
2. Определить хранилище секретов и передавать значения через закрытый env-файл вне репозитория. Требуются `SECRET_KEY`, исходный `FIELD_ENCRYPTION_KEY` для уже зашифрованных данных, отдельный `DLC_DB_PASSWORD`, `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, `TEST_SITE_BASE_URL=https://<test-host>/` и `TEST_CANONICAL_DOMAIN=https://<test-host>`. Значения домена должны совпадать с реальным HTTPS адресом; `PRIVATE_STORAGE_BACKEND` выбрать явно.
3. Для `PRIVATE_STORAGE_BACKEND=local` включить volume `dlc_private_data` в резервное копирование и восстановление вместе с PostgreSQL. Для `s3` передать все пять `PRIVATE_S3_*` параметров и до переноса проверить доступ, закрытость bucket, целостность и восстановление. Смена backend без переноса файлов оставит ссылки на отсутствующие объекты. Публичные `/media/` и `/static/` имеют отдельные volumes.
4. Выбрать Git remote, ветку выпуска и registry после проверки состава публикуемых файлов. Этот каталог сейчас без `.git`; не выполнять `git init`/`git push` автоматически. `.gitignore` закрывает локальные `data/`, дампы, медиа и env-файлы, но перед первым коммитом всё равно вручную проверить индекс на секреты, документы и резервные копии.

## Локальная проверка конфигурации

После получения утверждённых значений подготовить приватный env-файл и проверить раскрытую Compose-конфигурацию без запуска контейнеров:

```powershell
docker compose --env-file <private-env-file> -f deploy/compose.test-server.yml config --quiet
```

Отдельно убедиться, что в раскрытом `web` есть правильные `SITE_BASE_URL`, `CANONICAL_DOMAIN`, `PRIVATE_STORAGE_BACKEND`, `TEST_SITE_NOINDEX=True`, а DB/Redis не публикуют порты. Не выводить конфигурацию целиком в логи: она содержит секреты. Тестовый контур наследует production `DEBUG=False`, HTTPS cookies и PostgreSQL. Собрать образы и прогнать проверки на изолированной машине с подготовленными тестовыми данными; использовать неизменяемый тег образа, не `latest`.

## Перенос данных и открытие доступа

1. Остановить запись в исходную CRM, снять согласованную копию SQLite и всех файлов; проверить SQLite `integrity_check` и внешние ключи. Не переносить рабочую базу или ключи в публичный репозиторий.
2. В новой пустой PostgreSQL применить миграции отдельным одноразовым `migrate` до старта web. Текущий инструмент `scripts/local_preprod` принимает только loopback-цель; на удалённый PostgreSQL напрямую он не пишет. Его запуск возможен лишь внутри изолированного целевого хоста с локальной целью и проверенной копией. Повторный импорт в наполненную БД запрещён.
3. Сверить число и хэши таблиц, последовательности, файлы и FileField-ссылки. Снять PostgreSQL dump и восстановить его в **другую** базу; проверить совпадение. Для закрытых файлов проверить отдельное восстановление volume или bucket.
4. До открытия доступа выполнить `manage.py check --deploy --settings=dlc_montage.core.settings.prod`, проверку миграционного расхождения, полные тесты на отдельной PostgreSQL, `/health/`, вход, ключевые сценарии CRM, статику, отказ прямого доступа к private и отсутствие индексации тестового сайта. Затем проверить HTTPS, proxy headers и внешний барьер доступа через внешний адрес, в том числе ответы proxy и `/static/`/`/media/`. `TEST_SITE_NOINDEX=True` добавляет защитные сигналы приложения, но не заменяет барьер: [Google предупреждает](https://developers.google.com/search/docs/crawling-indexing/robots/intro), что `robots.txt` не скрывает URL от поиска; при запрете обхода робот также может не увидеть [`noindex`](https://developers.google.com/search/docs/crawling-indexing/block-indexing).
5. Зафиксировать порядок возврата к прежней версии и обращения с данными после новых записей. Откат образа не откатывает базу; прежнюю SQLite нельзя просто вернуть после работы на PostgreSQL.

Локальный preprod перенос от 04.10.2026 задокументирован в `22-local-preprod-cutover.md`: 51 таблица, 420 закрытых файлов и отдельная проверка восстановления. Это свидетельство предыдущего запуска, а не проверка текущего состояния и не готовый план непрерывного резервного копирования. Production deploy workflow пока намеренно блокирует внешнее исполнение до утверждения сервера и секретов.

## Выбранный временный адрес

По уточнению владельца от 10.10.2026 используем https://ai.penlite.de для временного сайта и кабинета. Будущий API может работать на том же домене под /api/v1/ после реализации API. Это выбор адреса, а не подтверждение настройки DNS, TLS или развёртывания. Значения TEST_SITE_BASE_URL=https://ai.penlite.de/, TEST_CANONICAL_DOMAIN=https://ai.penlite.de, ALLOWED_HOSTS=ai.penlite.de и CSRF_TRUSTED_ORIGINS=https://ai.penlite.de передаются через закрытый серверный env-файл. Запрет индексации и внешний барьер доступа сохраняются.
